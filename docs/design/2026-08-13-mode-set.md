# Exact set membership type (`ModeSet`)

**Status:** approved  
**Branch:** `feat/mode-set`

## Problem

SuperCache has opaque KV (`ModeCacheOnly` / `ModeLoadThrough`) and approximate membership (`ModeBloom`: Add / Test, no per-item delete).

There is no **exact set**: “is this item in the named set?” with **add, remove, and contains**, and optional enumeration. Callers today either:

- one KV key per element (RF, tombstones, and MaxBytes scale poorly), or
- keep sets outside SuperCache.

Bloom is the wrong tool when false positives are unacceptable or **removes** are required.

## Non-goals

- Sorted sets / scores, lists, hashes, HyperLogLog, Count-Min
- Set algebra RPCs (`SUNION`, `SINTER`, …) as first-class RPCs (can be client-side over Members later)
- Per-element TTL inside a set (whole-set `TTL` only, same as Bloom)
- Using sets as an internal index in front of every CacheOnly Get (separate design)
- Changing default RF, tombstone TTL, or existing Get/Put/Delete / Bloom contracts
- Persistence across process restart (same as KV / Bloom)
- Unbounded sets: `MaxBytes` still bounds the encoded entry

## Contract

### API (new; existing verbs unchanged)

On `pkg/engine.Engine`, `pkg/client.Client`, Cache proto, and `cmd/sc`:

| Call | Meaning |
|------|---------|
| `SetAdd(ks, name, item)` | Insert `item` into named set. Creates the set if missing. Idempotent if already present. |
| `SetRemove(ks, name, item)` | Remove `item` if present. No-op if missing or set missing. Does **not** delete the set name. |
| `SetContains(ks, name, item) (bool, error)` | Exact membership. Missing set → `false`, nil error (same spirit as BloomTest). |
| `SetCard(ks, name) (int, error)` | Number of elements (length). Missing set → `0`, nil error. |
| `SetMembers(ks, name) ([][]byte, error)` | All elements (defensive copies). Missing set → empty slice, nil error. Large sets cost memory/bandwidth — document; still v1 for parity with common set APIs. |
| `Delete(ks, name)` | Existing Delete: drops the **whole** set (tombstone on `name`). |

- `name` is a normal cache key (set identity); ring owner is `Owner(name)`.
- `item` is `[]byte`, same max length as a key (`MaxKeyLen` / engine limit).
- Get/Put on `ModeSet` → `ErrInvalidArgument` (wrong verb).
- Set* on non-`ModeSet` → `ErrInvalidArgument`.
- Bloom* on `ModeSet` (and Set* on `ModeBloom`) → `ErrInvalidArgument`.

### Keyspace

New mode `keyspace.ModeSet`.

No extra sizing knobs in v1 (unlike Bloom’s `m,k`). Capacity is whatever fits under `MaxBytes` after encoding.

| Field | Role for ModeSet |
|-------|------------------|
| `MaxBytes` | Bounds encoded set blob + envelope |
| `TTL` | Expires the **whole** set entry if set |
| `NegativeTTL` | Ignored |
| `TombstoneTTL` | Applies when the set name is Deleted |
| `ReplicationFactor` | Same as KV / Bloom |

`UpdateKeySpace` still wipes the in-memory store for that keyspace (same as today).

### Replication

Same owner + `R-1` successors as KV. Owner = `ring.Owner(name)`.

**Mutations must not LWW-replace the whole set on every peer with an unrelated concurrent op’s snapshot in a way that drops elements** if we ever allowed multi-writer. **v1 locks owner-coordinated writes** (same as Put / BloomAdd): non-owners forward to the owner; owner applies, then fans out.

Two fan-out options considered; **locked choice: item-level apply ops** (parallel to BloomAdd), not full-set LWW on every Add/Remove:

| Op | Owner | Replicas |
|----|--------|----------|
| `SetAdd` | insert item under store mutex; bump version when set created or membership changes | `ApplySetAdd` (insert item; create empty set if needed unless tombstoned) |
| `SetRemove` | remove item under mutex; version bump when membership changes | `ApplySetRemove` |
| `Delete(name)` | existing tombstone path | `ApplyDelete` |
| Join handoff | full membership snapshot | `ApplySetMerge` = **replace-if-newer version** with decoded member list **or** union-merge at equal policy below |

**Handoff / snapshot rule (locked):** ship `FlagSet` entry with encoded members + `Version`. Receiver:

- if local tombstone version ≥ incoming → ignore;
- else if incoming version ≥ local set version → **install snapshot** (not pure union of stale local adds), so removes observed on the owner are not undone by a lagging replica’s extra members;
- else ignore older snapshot.

Item-level applies carry the owner’s **set version after the op** so a replica can ignore ops older than a handoff snapshot (same idea as version gates on ApplyPut).

Failed replica applies: existing hint path. Hint identity:

- add: `(ks, name, "add", item)` so two adds are not coalesced away;
- remove: `(ks, name, "rem", item)`;
- tombstone on `name` supersedes pending add/remove hints for that name (same as Bloom).

Non-replicas: `SetContains` / `SetCard` / `SetMembers` **forward to owner** (like CacheOnly miss / BloomTest). Do **not** keep a full set copy on non-replicas by default (sets can be large). Optional later: RF copies only (same as today for bloom bitsets on replicas).

Replicas in the RF set hold a full local copy for Contains without a network hop (same as Bloom bitset on replicas).

### Concurrent Add/Remove of the **same** item

All client writes for a name go to the **owner**, which serializes ops. Order is well-defined: last op wins for that item (add then remove → absent; remove then add → present). Replicas apply the op stream (or later snapshot) and converge.

### What existing clients can still assume

- CacheOnly / LoadThrough / ModeBloom behavior bit-identical if they never open `ModeSet`.
- No new default keyspace.
- Peer proto gains apply RPCs; rolling upgrade: deploy peer RPCs before relying on set fan-out (same class as Bloom).

## Approach

### Encoding (`pkg/set` or `store` helpers)

Canonical membership blob in `store.Entry.Value` with `FlagSet`:

- Sequence of elements: for each item, `uvarint(len)` + raw bytes.
- Elements stored **sorted by raw byte order** so equal sets encode identically (handy for tests and diffs).
- Decode → in-memory `map[string]struct{}` only inside store methods (key = `string(item)` for map; document that item bytes must not rely on invalid UTF-8 — Go string map keys are fine for arbitrary bytes).

Package `pkg/set` (optional thin helpers): `Encode([][]byte) []byte`, `Decode([]byte) ([][]byte, error)`, `Contains`, `Add`, `Remove` on a small `Set` type used by store.

### Store

New flags:

```go
FlagSet       // value is encoded set membership
FlagSetAdd    // fan-out: value is one item to insert
FlagSetRemove // fan-out: value is one item to remove
```

Under the store mutex:

- `SetAdd(key, item, version, expireAt) bool` — create or update; reject if tombstone with version ≥; return false if no-op rejected by tombstone.
- `SetRemove(key, item, version, expireAt) bool`
- `SetContains` / card / members via Peek + decode (or specialized methods).
- Protect live set entries from LRU eviction the same way live tombstones/blooms are protected if that policy already exists for Bloom; **match Bloom’s eviction rules** for structured flags.

`AcceptIfNewer` on a plain blob must **not** clobber `FlagSet` with a non-set put (engine already blocks wrong-mode Put).

### Engine

Mirror Bloom routing:

1. Validate mode `ModeSet`, key/item limits.
2. Owner path: local store op + `replicate` of `FlagSetAdd` / `FlagSetRemove` entry (version = post-op set version).
3. Non-owner: forward (new Cache is client→node; within cluster use peer Forward or Apply pattern).  
   **Locked for v1:** non-owner **SetAdd/SetRemove** use the same pattern as Put: forward to owner (`ForwardPut`-style or dedicated `ForwardSetAdd` — prefer **dedicated peer RPCs** for clarity, or overload Apply with flags via existing ApplyPut carrying `FlagSetAdd` like Bloom already does with ApplyPut + FlagBloomAdd).

**Locked wire approach (minimal proto churn):** reuse **ApplyPut** with flags (Bloom already does FlagBloomAdd on ApplyPut path). Engine `ApplyPutWithRingGen` branches:

- `FlagSetAdd` → `applySetAdd`
- `FlagSetRemove` → `applySetRemove`
- `FlagSet` → snapshot install with version gate
- existing FlagBloom* / KV / negative unchanged

Cache API still gets first-class `SetAdd` / `SetRemove` / … RPCs (user-facing). Peer mesh can avoid new RPC names if ApplyPut flag dispatch is enough; handoff uses `FlagSet` snapshot via existing handoff ApplyPut.

If ApplyPut flag dispatch is too overloaded for review, add `ApplySetAdd` / `ApplySetRemove` / `ApplySetMerge` peer RPCs explicitly (Bloom eventually added dedicated names in design — implementation used flags on ApplyPut). **Prefer flag-on-ApplyPut for v1** to match current Bloom implementation path and less gen churn; document flags in peer comments.

### Client / sc / OpenAPI

- `pkg/client`: SetAdd, SetRemove, SetContains, SetCard, SetMembers.
- `cmd/sc`: `set add|rem|contains|card|members`.
- OpenAPI cache spec: document new RPCs.

### Rejected alternatives

| Idea | Why not |
|------|---------|
| Overload Get/Put | Put is replace-one-value; set needs multi-item ops and remove |
| Grow-only set (no Remove) | User asked for sets; remove is core |
| Full-set LWW fan-out every Add | Correct under single owner but O(n) network per Add; item-level is enough with owner serialize |
| Redis wire protocol | Different product surface |
| CRDT OR-Set with per-add tags | Heavier; owner serialization makes it unnecessary in v1 |
| Store each element as its own key `name\\0item` | Multiplies RF keys and Delete semantics; hard card/members |

## Benchmarks (sets)

Ship **set-specific micros** in the same style as `BenchmarkStoreGetHit` / `BenchmarkEngineGetHit` (`-benchmem`, `benchmetrics.ReportB` where engine already does). CI already runs:

```text
go test ./pkg/store ./pkg/engine -bench='Benchmark(Store|Engine)' -skip=Cluster3 ...
```

so any new `BenchmarkStoreSet*` / `BenchmarkEngineSet*` names are picked up automatically and appear in the PR micro table (baseline `main` will lack them until first merge — that is fine; after that they get A/B).

### Store (`pkg/store`)

| Benchmark | Setup | Op |
|-----------|--------|-----|
| `BenchmarkStoreSetAdd` | one set key; items `i%N` (N=1k) | `SetAdd` under mutex (idempotent after warm) |
| `BenchmarkStoreSetContainsHit` | prefill N=1k members | `SetContains` true |
| `BenchmarkStoreSetContainsMiss` | same prefill | `SetContains` false for never-added item |

### Engine single-node (`pkg/engine`, `ModeSet`)

| Benchmark | Setup | Op |
|-----------|--------|-----|
| `BenchmarkEngineSetAdd` | one set name; item `i%N` | `SetAdd` (create + steady idempotent adds) |
| `BenchmarkEngineSetContainsHit` | prefill N members on one name | `SetContains` → true |
| `BenchmarkEngineSetContainsMiss` | same | `SetContains` → false |
| `BenchmarkEngineSetRemove` | prefill; re-add outside timed path if needed | `SetRemove` (or add+remove pair with restore outside timer — prefer steady remove of rotating members with re-add outside `b.N` timing like Delete benches) |
| `BenchmarkEngineSetCard` | prefill N | `SetCard` |
| `BenchmarkEngineSetMembers` | prefill **small** N (e.g. 64), fixed | `SetMembers` (copies all; documents alloc cost) |

Parallel variants (`…Parallel`) for **ContainsHit** and **SetAdd** only (same pattern as GetHitParallel / PutParallel). Skip parallel Remove/Members in v1.

### Regression rules for the ModeSet PR

1. **Existing** Get-hit / StoreGetHit **allocs/op** must not rise (set code must not sit on KV Get).  
2. **New** set micros: establish baseline on first merge; later PRs treat ±20% ns/op as noise only if **set** allocs/op stay flat on ContainsHit.  
3. Smoke scbench: still noise-only for ModeSet as long as (1) holds.
